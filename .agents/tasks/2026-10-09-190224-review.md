### Venue delete: non-nullable courtId nullification

The delete handler at `DELETE /admin/venues/:id` runs this before deleting the venue:

```js
await prisma.booking.updateMany({
  where: {
    court:  { venueId: id },
    status: { in: ['COMPLETED', 'CANCELLED', 'NO_SHOW'] },
  },
  data: { courtId: null },
});
```

The Prisma Booking model declares `courtId String` — not `courtId String?`. Prisma's type-safe client will throw `Invalid value for argument "courtId": expected String, got Null` before issuing any SQL. The intent was to orphan historical bookings cleanly before the cascade deletes courts, but the schema doesn't allow it.

The correct fix requires a migration. Two viable paths:

1. Add `onDelete: SetNull` to the `court` relation in Booking and change `courtId` to `courtId String?`. This preserves historical bookings with a null court reference, which is the intended behavior.
2. Add `onDelete: Cascade` to the `court` relation in Booking (and accept that deleting a venue cascades through courts into bookings). This is a data-loss path and must be explicitly authorized.

Until the migration is applied, the delete endpoint will return a 500 for any venue with completed/cancelled/no-show bookings, even though the active-booking guard would have allowed deletion.

### Phone search partial fix

The booking search query after the partial fix:

```js
where.OR = [
  { playerName: { contains: search, mode: 'insensitive' } },
  { phone:      { contains: search } },  // ← mode missing
];
```

An admin searching "0300" for a phone number will get case-insensitive results for names but collation-dependent results for phone numbers. The fix is a one-word addition: `{ phone: { contains: search, mode: 'insensitive' } }`.

### Confirm dialog button color for non-destructive actions

When an admin clicks "Complete" on a CONFIRMED booking, the confirm dialog renders the action button in `var(--brand-danger)` (red). The condition is `confirmDialog.newStatus === 'CONFIRMED' ? gradient-cta : brand-danger`, so COMPLETED, NO_SHOW, and CANCELLED all share red. Completing a booking is not a destructive action. This is cosmetic but misleading. A neutral color (the existing `var(--gradient-cta)`) for COMPLETED and a secondary color for NO_SHOW would communicate intent accurately.
